# Chippi

A Windows 11 tray app for the owner's own PC (C#, .NET 10, WPF): a widget on the desktop (a puck with the pet) that opens a panel with a page per feature (Audio, Clipboard, Scratchpad, Shelf, System, Keep awake, File organizer and more), and a Settings window. GitHub: `tcurtsinger/Chippi`.

- **Design:** `DESIGN.md` wins over taste. Mockups are under `docs/**/design/`.
- **Impeccable** (v4.11.0) is in `.claude/skills/impeccable`. `DESIGN.md` wins over its defaults. Its screenshot, live and detector tools are web-only and don't run on WPF.
- **Plans:** `PLAN.md` has the phases. Each phase's brief is `docs/phase-N-handoff.md`, with its `behavior-spec.md`, `architecture.md` and report beside it.
- **Hopper** (`X:\code\hopper`) is reference only. Never change it.

## Build

- The .NET SDK (10.0.403, from `global.json`) is at `C:\Program Files\dotnet`, which isn't on PATH. Prepend it in each shell.
- Build like CI, once per runtime: `dotnet build src/Chippi.App/Chippi.App.csproj -c Release -r win-x64 --no-incremental`, then `win-arm64`. The SDK rejects `-r` on `Chippi.slnx`.
- Warnings are errors.
- From PowerShell 5.1, run dotnet through `cmd /c`, so its stderr isn't turned into errors.
- `build/pack.ps1` publishes the admin helper with NativeAOT, which finds the linker through `vswhere.exe`: prepend `C:\Program Files (x86)\Microsoft Visual Studio\Installer` too, or the publish fails with "'vswhere.exe' is not recognized".

## Test

- CI runs every project under `tests/` in Release on x64, in its own job beside the two builds. It builds `Chippi.slnx` once and runs the tests without building again, so a new test project must be in `Chippi.slnx`. Locally, run the projects your change touches, and let CI run the rest. A test file other projects link (`tests/Chippi.Island.Tests/WpfTestThread.cs` is in six feature test projects) needs `dotnet build Chippi.slnx -c Release` before you push. Through `cmd /c`, a `|` in `--filter` is a pipe, not "or": run one filter at a time.
- CI runs once per pull request and once on `main` after a merge, not on branch pushes. A change that only touches Markdown, `docs/` or `phase-1-release-artifacts.csv` runs no CI.
- Run in Release too when a test touches Debug-only members.
- `Chippi.UiSmoke` drives real windows and keys on the desktop. It's skipped unless `CHIPPI_UI_SMOKE=1`; only enable it when the owner has set a time (`tests/Chippi.UiSmoke/README.md`).
- **Nothing that shows windows on the owner's desktop runs locally while he's at the PC:** `Chippi.Island.Tests`, `Chippi.SoundSmoke` and other projects that open windows, `--island-pages`, `--island-shots`, `CHIPPI_SWITCHER_LIVE`, UiSmoke and dev runs that show the widget. They take his keyboard and mouse (the owner, 2026-11-07: "I cant do anything while it runs"). CI runs those test projects; locally, run only the projects without windows, and take screens with the offscreen shots (`CHIPPI_ISLAND_SHOTS` tests, `--settings-snapshot`). An on-screen run needs the owner to say he's away. Offscreen renders and windowless tests may still run while a game or Zoom is in front (the owner, 2026-10-29).
- The CI runner's GPU has no engine counters, so tests that read hardware must accept null readings.
- `Chippi.App` internals outside the island (`Shell/ShellLifetime`, startup folder) are tested windowlessly in `Chippi.Notifications.Tests`, which has InternalsVisibleTo; `Chippi.Island.Tests` shows windows.
- Clipboard fakes behave like the real clipboard thread: `FakeClipboard` returns a cancelled task for a cancelled token, so a restore after a paste swap uses `CancellationToken.None` (`RestoreWithRetryAsync`). Rewrite a copy read earlier with `IClipboardHub.WriteIfCurrentAsync`; plain `WriteAsync` overwrites a newer copy.
- `VbCablePackage.Prepare` holds the checked setup open until `Release`; a test that prepares releases it before deleting its temp folder.
- Feature test projects build controls without the app's themes, so a control there has default templates: test sizes, alignment and fit in `Chippi.SoundSmoke` or `Chippi.Island.Tests`, which load them, or in the shots.
- Sound UI tests run on the shared `SoundUiThread` dispatcher through fixture disposal. A fake device can report a new default before the picker command has finished releasing its audio role.
- A test `AudioService` has no UI context, so `VbCableRequirement` computes its state on the test's thread and the engine's at once. A file another thread is deleting reads as not found, access denied or a sharing violation after `File.Exists` said true; its tests inject the marker read (`readMarker`) for each, and hold one scan in it to show an older scan never sets the state over a newer one.
- Sound modules await `AudioService.ReadyAsync` after acquiring their lease; `RefreshAsync` forces an expensive endpoint scan. Default-only events and role picks reuse the catalog and publish confirmed defaults immediately. Device topology/name/state changes invalidate it and keep the 400 ms Bluetooth debounce. Audio timing probes must refuse all device writes and never start playback or capture on the owner's PC.
- Tests never take the owner's foreground: a page that takes the keyboard activates the island through `IslandPanelWindow.ActivateWindow`, which island tests stand in for.
- The module registry starts and stops every module on the calling (UI) thread and never uses `ConfigureAwait(false)`; modules capture their start thread as the UI thread. On a `WpfTestThread`, wait on a registry call with `WpfTestThread.Wait(...)`, never `.GetAwaiter().GetResult()`, which hangs once a module awaits real work. Dev profiles seeded with Scratchpad alone never reach such a module (Audio routing, Clipboard history with data), so threading bugs there need a test.
- Make a flaky test deterministic with injected timers and clocks, not longer waits: the panel's morph and the controls' fill fades step each frame from a clock a test can hold (`IslandPanelWindow.Clock`, `FillFade.Clock`). Local runs share the owner's real mouse, so tests that press the widget pin its pointer (`IslandWindow.PointerAt`), and the island tests' hooks ignore the real keyboard and mouse (`IslandWindow.WatchesInput`). Wait for the panel's open, page or close with `IslandWindowTests.Settle`, not a fixed pump.

## Run it

- **Never against the real profile.** `CHIPPI_DEV_PROFILE=<name>` (or `--dev-profile <name>`) gives a run its own instance, settings (`%APPDATA%\Chippi-dev\<name>`) and logs (`%LOCALAPPDATA%\Chippi-dev\<name>\logs`). A dev profile is single-instance.
- Seed a dev profile before starting it: `{"version":1,"modules":{},"features":{"preset":"custom","installed":["scratchpad"],"capabilitiesUsed":[]}}` starts just Scratchpad. Use an empty installed list for a shell-only run. A missing version makes the settings unreadable and starts the Essentials preset instead.
- **Never install Sound modules in a dev profile:** routing claims the owner's default devices.
- **Focus follows mouse:** native access is refused in dev profiles, before reading its user-wide ownership journal. Its UI tests inject settings; real Windows tracking checks run only in Sandbox, using a normal profile inside that isolated Windows session.
- **AI agent usage in a dev profile** starts the owner's real `claude` and `codex` for its checks (about 1.5 s each, every 5 minutes, every minute while its page shows) and reads his sessions' files. Install it only for a run that needs it, and end the run once it's done. Its tests use fixtures; `CHIPPI_AGENTS_TIMINGS` and `CHIPPI_AGENTS_SCAN_TIMINGS` name reports for the page's open and the 5-second scan.
- **Snapshots without showing anything:** a Debug build run with `--debug` saves PNGs to a folder with `--island-pages <dir>`, `--island-shots <dir>`, `--settings-snapshot <dir>` or `--flyout-snapshot <dir>` (the tray menu).
  `--island-pages` and `--island-shots` show the widget and the panel on screen; both shoot dark, then light. A click elsewhere closes the panel mid-run, and the widget hides while a fullscreen app is in front on its display, so check the shots. `--island-shots` also drops the widget in each corner and past every edge and checks where it lands (`r6-drop-check.txt`).
  `--settings-snapshot` also shoots Settings › Text snippets at 860 width (`r6-snippets-narrow-*`); its states (editor, refusals, search, the date picker, Delete) are offscreen shots in `Chippi.Features.TextSnippets.Tests` under `CHIPPI_ISLAND_SHOTS`.
  `--settings-snapshot` also shoots the Shortcuts editor's states (`r6-editor-*`: new, listening, Caps Lock, ready, refused) at full and 860 width without recording, so it never takes the keyboard. Seed the dev profile with a few bindings on chords no app uses, and leave Caps Lock combos and Mouse buttons off. It then opens each feature's Edit link as a click does (`r6-edit-<feature>-*`, the editor in that row) with a stand-in recorder, and times each in `r6-edit-timings.txt`. Two dev runs at once hold each other's chords, so the second shows "Shortcut in use".
- **Shots in tests:** the offscreen page shots run when `CHIPPI_ISLAND_SHOTS` names an output folder. Settings › Snap, its zone editor and the Shift+drag zones render from `Chippi.Features.WindowLayouts.Tests` (`SnapPageTests`) without showing the overlay window. They render dark; `CHIPPI_SHOTS_THEME=light` renders them light. The island follows the app theme. The Radial menu's shots (`RadialMenuShots`) use the same variables, and `CHIPPI_RADIAL_TIMINGS` names a report of its opening and pointing times. `CHIPPI_SWITCHER_TIMINGS` names a report of the App switcher engine's times with 50 windows (reading them cold and warm, each search keystroke); the overlay's own opening is timed in the Sandbox, since it takes the foreground.
- **Arrangements native placement:** the Sandbox runner's `-Checks arrangements` creates twelve disposable editor windows and checks shared shortcuts, reuse, relaunch, window state and focus. It also checks Settings capture and Save, Cancel, timeout, admin refusal and a launched fullscreen window. Its README lists the remaining physical-display and app-specific owner checks. Run it once with the completed feature.
- **Arrangements screens:** Settings › Snap › Arrangements (the list, the review, Edit, refusals, a launch from Settings) render offscreen from `ArrangementPageTests`, and Actions › Snap › Arrangements, the run page's states and the bar's lines from `ArrangementIslandTests`, both in `Chippi.Features.WindowLayouts.Tests` with the shot variables above and fake desktops, so nothing launches or moves. `CHIPPI_ARRANGEMENT_TIMINGS` names a report of the pages' opening and the run page's response. `--settings-snapshot` also shoots Settings › Snap scrolled to Arrangements at full and 860 width (`r6-snap-arrangements-*`): seed the dev profile's `window-layouts` module with arrangements whose `arguments` and `workingFolder` are strings, or the section is refused and logged.
- **Sandbox waits:** use forward slashes in paths passed to Serenity `wait --until`, for example `powershell.exe -NoProfile -File X:/code/chippi/build/fullscreen-check.ps1`. Its command parser strips unquoted backslashes. The Sandbox runner always rechecks the gate before starting.
- **Arrangements discovery (read-only):** set `CHIPPI_ARRANGEMENTS_DISCOVERY` to a report file and run `dotnet test tests/Chippi.Island.Tests/Chippi.Island.Tests.csproj -c Release --filter FullyQualifiedName~ArrangementDiscoveryTests`. It reads registered targets and captures a draft without launching, moving or activating windows, and records counts and timings only. The final launch/placement proof belongs in the feature's Sandbox run.
- **Snap:** Chippi.Features.WindowLayouts.Tests renders the Settings page, zone editor, Actions menu and overlay offscreen with the shot variables above. The native check is tests/Chippi.Input.Tests/Sandbox/run.ps1 -App <self-contained app folder> -Out <new session temp folder> -Checks snap. It uses an isolated dev profile, two Notepad windows (standard editor windows when Notepad is absent), UI Automation and real title-bar drags. A single-display Sandbox cannot prove physical mixed-DPI placement or monitor removal.
- **The App switcher's overlay, live:** `CHIPPI_SWITCHER_LIVE=<dir>` runs `SwitcherScreensTests.Live_overlay_with_previews`: the real overlay, never activated, on the second display when there is one, over 12 and then 50 of the test's own windows with Windows' live previews drawn in. It saves screen captures and `switcher-live-timings.txt` (open, search keystrokes, arrow keys). Run `build/fullscreen-check.ps1` first; it shows on the desktop for about two seconds. Its board and page shots use `CHIPPI_ISLAND_SHOTS`, which leaves the preview slots blank because Windows draws them.
- **The capture layer** (`Chippi.Capture`, `Chippi.UI.Capture`, docs/phase-7/capture-layer.md): its geometry and the selector's clicks, drags and keys are tested without windows in `Chippi.Capture.Tests`. `CaptureOverlayShots` in `Chippi.Island.Tests` renders the overlay's states over a synthetic frozen screen at 100% and 150% with `CHIPPI_ISLAND_SHOTS` (`capture-*.png`), showing nothing. The real overlay reads the screen, so it runs only in the Sandbox: a Debug self-contained build with `run.ps1 -Checks capture` (its README). `CHIPPI_CAPTURE_TIMINGS` names a report of key to frozen screen and release to bars.
- **Capture host:** `CaptureHostTests` in `Chippi.Island.Tests` checks reentrant shortcut registration, tools-only mode, the shared command and removal of the last provider. The App host supplies the shared tile through `ModuleServices.SharedIslandTiles`; provider Settings rows edit owner `capture`. The completed feature is checked with the Sandbox runner's `-Checks screen-capture`.
- **Shell layout checks:** in Debug, `IslandPanelShots.RenderToolGallery` captures homes with ten, five and two tools. `IslandPanelShots.RenderPortraitHome` renders a 900px portrait display at 200% scale. `AgentBarTests.Render` captures working and waiting AI sessions with fixture data and controlled timers, using the same shot variables.
- **Widget-to-panel motion:** the widget and panel have separate layered windows. To check the handoff, capture both in the same fixed desktop region over an isolated backdrop. Sample DWM presents from before release, including several cold opens. Rendering the panel alone or holding its clock can miss a one-frame flash.
- **Panel reopen:** `PanelRetainedFrameTests` checks the native layered-window hit mask entirely offscreen, without screen reads or input; it seeds a fixture frame because WPF may skip offscreen drawing. Hiding stops WPF before it presents the last close frame, so suppress the retained native surface after hiding; resetting the managed shape alone can flash the old panel on the next Show. A real-rendering probe can use a private Win32 desktop without switching to it: verify its desktop name before showing anything and use fixture content and isolated logs. `PrintWindow` can ignore the layer's constant alpha; its cached RGB alone does not prove the image is visible.
- **Puck drag direction:** compare the native window's presented pixels and the pointer as it crosses the display midpoint in both directions. Layout alone can miss a frame where the layered window still shows its old pixels. Use an isolated desktop for the drag probe.
- **The pet's sheets:** `--pet-sheet <dir>` and `--pet-motion <dir>` render offscreen. Seed `"islandEnabled": false` in the dev profile and nothing shows at all. `CHIPPI_PET_SHOTS=<dir>` renders the sheet from the tests.
- **Measuring the widget's CPU while a fullscreen app holds the main display:** it hides there, so seed the dev profile's widget onto another monitor (`"islandDisplay": "specificMonitor"`, `"islandMonitorId"` the monitor's `\\?\DISPLAY#…` path), and read the process's CPU time over 45 to 60s, three times: single readings swing by half. The owner's own puck may sit in the same corner; end the run as soon as it's read.

## The owner's PC

- **Real input:** never click or type on the desktop while a fullscreen app or Zoom is in front; `build/fullscreen-check.ps1` exits 1 then. Never send keys blind: confirm what's in front first.
- **Clipboard:** never read, write or log the owner's real clipboard. Clipboard and input checks run only in Windows Sandbox (a `.wsb` with clipboard redirection and networking off). A probe there drives the real hooks with `SendInput`: the input hub passes on untouched only input Chippi sends itself (`ChippiInput.Marker` in its extra info), so a probe's input counts as a hand's.
- **Input checks in the Sandbox:** `tests/Chippi.Input.Tests/Sandbox/run.ps1` (its README) runs a self-contained build there against a target window and writes what arrived; it refuses while a fullscreen app is in front or another Sandbox runs. `dotnet publish` needs `pwsh` for the soundboard tools, so build the app self-contained instead.
- **The taskbar (Mac-style desktop):** only the real profile hides the real taskbar; dev profiles and tests never touch it, not even to give it back (`MacDesktopModule` gets no takeover). Hiding it runs only in Windows Sandbox or an owner-approved away session, never on the owner's desktop while he's at it. If it's ever left hidden, `Chippi.exe --restore` gives it back at once (also with Chippi stuck or gone) and turns the mode off; a start with the mode off, and uninstall, do the same. Its logic is tested against a fake shell in `Chippi.Features.MacDesktop.Tests`.
- **The menu bar (Mac-style desktop):** `MenuBarOffscreenTests` in `Chippi.Features.MacDesktop.Tests` builds the real bar without a window (`MenuBarWindow.LayOut`) and checks what takes a press, what a narrow bar drops and each group's ink; with `CHIPPI_ISLAND_SHOTS` it saves `menu-bar.png`, `menu-bar-2x.png` and `menu-bar.txt` (the bar over light, dark and split wallpapers, with a notch, at 1920, 960 and 640). An offscreen hit test uses `VisualTreeHelper.HitTest`: `InputHitTest` skips everything that isn't on a screen. Menus of the bar and the dock open through `BarMenu`, which holds the keyboard with `MenuFocus`; a row that acts in the app in front sets `InFront`, and a question is `BarQuestion.Ask`. Their look, the keyboard and the fullscreen rule on two displays (`FullscreenHolds`, tested pure) are checked live only in the Sandbox or an away session. The volume is only ever read (`VolumeReading`). App names come from the Start menu's list (`AppCatalog`, read once on a thread of its own; its matching is pure and tested), and the shots' `menu-bar.txt` also lists what this PC's open programs would be called. The right side is Chippi's own items (`BarItems`: what shows, what can be added and what a press does are pure and tested); they run the features' commands and pages by key, and `MenuBarItemKeysTests` in `Chippi.Notifications.Tests` holds those keys against the features' constants, since the menu bar's project doesn't reference them. Windows' own flyouts are never moved. The Settings section renders with the app's styles only in a `--settings-snapshot` run (`r6-mac-desktop-on-*`, its sections as with the mode on); seed the dev profile's `mac-desktop` with `"style": "windows"`, so no bar shows.
- **The dock (Mac-style desktop):** `Chippi.Features.MacDesktop.Tests` is windowless (clicks, the fit, icon pixels). With `CHIPPI_ISLAND_SHOTS` it saves `dock-icons-rest.png`, the dock's own icon path on Windows' icons at 48, shown 6 times; `CHIPPI_DOCK_SHOT_ITEMS` adds shortcuts or programs, separated by `|`. `DockGlideTests` lays the row out offscreen and saves `dock-glide.png` and `dock-glide.txt`: one icon's edge per quarter-DIP of pointer, as each slot rounded on its own drew it and as it's drawn now. Magnification is drawn, not laid out: `DockLayout.Slots` gives each tile a whole-pixel slot and its icon an exact scale and shift (`DockTile.Place`); setting an icon's size through layout brings back whole-pixel steps under a slow pointer. The dock itself shows windows: its clicks, menus and magnification are checked only in the Sandbox or an away session. To bring another app's window forward use `ForegroundRight.Show` (un-minimize, then the foreground); `WindowAction.Restore` is Snap's undo and refuses a window it didn't snap. Windows hands icon pixels over with straight alpha: `WindowsAppIcons` premultiplies them (`IconPixels`), and anything that scales an icon does it after that.
- **Hooks:** no feature hooks the keyboard or mouse itself. It adds a filter to `ModuleContext.Input`, the shell's one input hub (`Chippi.Input`, docs/phase-6/architecture.md section 2), and its tests feed the filter by hand or use the hub's fakes in `Chippi.Input.Tests`. `CHIPPI_INPUT_TIMINGS` names a report of the hooks' time per event. A filter that tracks swallowed keys clears that ownership in `InputReset`, called on the hub thread after a desktop switch or lost hook forgets ownership. Ordinary resets keep swallowed repeats and ups until release.
- **Caps modifiers:** use `IInputRegistration.HoldModifiers` for each unbound key, never feature-owned input injection. The hub shares modifiers across overlapping keys, skips physical modifiers, and releases its own on every safety path. `IInputHub.ForegroundElevated` is cached outside hook calls; Caps passes unchanged when it is true.
- **Actions:** no feature sends keys, moves windows or opens programs for an action itself. It runs each `ChippiAction` with an `ActionRunner` over `ModuleContext.Actions`, the shell's one PC (`Chippi.UI.Actions.WindowsActionPc`), and edits it with `Chippi.UI.Actions.ActionPicker` and `KeyRecorder`. Its tests pass a fake `IActionPc`.
- **Shortcuts:** no feature registers a hotkey itself. It adds each shortcut it offers to `ModuleContext.Shortcuts` (`Chippi.Core.Shortcuts`) when it starts, set or not, and disposes it when it stops; Settings › Shortcuts lists the features in that list, and it's the only place a shortcut is recorded: a feature's own page shows its keys read-only with `ShortcutSetting` (Chippi.UI) and Edit, which calls `ModuleContext.EditShortcut(name)` to open the editor in that row (the owner, 2026-11-05). For a shortcut owned by another module, call `ModuleContext.EditShortcutFor(owner, name)`; capture pages use owner `capture` for Open Capture. It passes `ShortcutEdits` (its saved keys, Change and Remove), so Settings can change it; the editor refuses a clash with the service's `Check` before the feature sees it. A real-Windows check of `Check` needs only `RegisterHotKey` (the real `HotkeyWindow`), no key presses. Its tests pass a fake `IHotkey` factory, or a `ShortcutService` over a fake `IHotkeyRegistrar`. A dev run shows a Chippi clash only on a chord no other app holds: another app held Ctrl+Alt+Space on 2026-11-05. Print Screen is the one key bindable alone; while a shortcut holds it, the service turns off Windows' "Use the Print screen key to open screen capture" and puts it back after. It turns it off before registering the key (registered while Windows' is on, Print Screen reaches Chippi only with a Chippi window in front), and lets go of the key while Windows' switch is back on. Only the real profile's Chippi.exe touches that setting: dev profiles and tests get `MemoryPrintScreenSetting`.
- **Foreground:** a window Chippi shows gets the foreground right after a shortcut (`WM_HOTKEY`), an island click or Search, but not after a press the input hub swallowed (the Radial menu, mouse buttons, Caps Lock combos). There, one tap of the unassigned key 0x07 marked with `ChippiInput.Marker` earns it, then try once more, never in a loop (`WindowsSwitcherPc.TakeForeground`). To hand the keyboard on, activate the other window while yours still holds the foreground, then hide yours: hiding first lets Windows pick, often another Chippi window (the App switcher's spike, Windows Sandbox, 2026-11-05).
- **Ask first** before installing anything or changing the audio setup.
- **No sound** without warning.
- **No CPU stress tests:** one froze the PC.
- **Logs:** tests never write the real `chippi.log`. `tests/Directory.Build.targets` gives them their own (`SmokeLog.cs`).
- **Startup and quit:** a failure before the tray exists exits with code 1, so no invisible Chippi keeps the single-instance lock. Quit waits at most 10 s for modules to stop; OnExit stops modules that started on every other way out (logoff 4 s, failed start). A `settings.json` still held by another program after about 2 s fails the load instead of starting on defaults, which a save would write over his settings.
- **Settings saves in a click handler** catch `IOException`, `UnauthorizedAccessException` and `InvalidOperationException`, roll back a chord they just registered and report "Save failed" (`AppSwitcherModule` is the model). A feature keeps its `IHotkey` from start to stop: a rollback or Remove calls Unregister, and only stopping disposes it (`CommandBarModule`).
- **File moves across volumes** copy named streams (Zone.Identifier) with `FileHandles.CopyAlternateStreams` after the exclusive partial handle is released, since `FileShare.None` blocks opening them. A destination without named streams skips them.
- **Dev notifications:** a dev profile that shows toasts leaves an HKCU COM class and a Start Menu `Chippi-dev-<profile>.lnk`; clean them with `--cleanup-dev-notifications` after the run (`src/Chippi.App/Notifications/README.md`).
- **Explorer menu:** tests never change the owner's Organize entry. Only Chippi.exe changes the real menu (`ExplorerRegistration.CanChange`), so a test-hosted `DownloadsModule` has no registration; a test of the verb injects one under its own key.

## How work goes

- **One branch and worktree per change**, in `%LOCALAPPDATA%\chippi-work\<name>`, kept only while its PR is open: once it merges, remove the worktree and its local branch, and `chippi-work` itself when nothing else is open. The main checkout, `X:\code\chippi`, is the source of truth and the only Chippi folder that lasts (the owner, 2026-10-31); never add one to `X:\code`. Work in a worktree, never in its files, but keep its `main` current (see Merging).
- **Size:** one PR per feature, engine and screen together, opened when the feature is done. Don't stack PRs on another PR's branch: merging that branch closes them.
- **Who builds what:** Lumen (UI/UX) builds the screens from her mockups; the developers build engines, wiring and probes, and review her code (the owner, 2026-11-05).
- **Review:** another agent reviews each PR once, when it's ready. The author fixes the findings and CI confirms; a second look only for a fix that changes behavior. Minor notes are fixed in passing or dropped, never a round of their own. Changes to `Chippi.Input`, the hub every input feature shares, get a full review. Call out new projects in `Chippi.slnx`, and changes to shared code (Core, App, the island, Chippi.UI), in the PR.
- **Tests:** CI is the test gate. The author runs the projects the change touches once before pushing; reviewers read and don't rerun suites. A Sandbox check runs once per feature, at the end, and again only if the input path changed (the owner, 2026-11-05: "Going forward, the team should only be reviewing each others work at larger intervals. Same with running the tests.").
- **Merging:** a PR merges only when every CI job is green, with a merge commit. A PR that runs no CI merges once it's reviewed. Don't wait on `main`'s run after a merge: check it's green before you open the next PR.
- **After a merge,** bring `X:\code\chippi` up to date in the same turn: `git fetch`, then `git merge --ff-only origin/main` (the owner, 2026-10-31). Check `git status` first and never discard his changes: if a tracked file is modified, or the merge would overwrite an untracked file that isn't empty or the same as `main`'s, stop and ask him.
- **Scratch:** shots, probes and review notes go in your session's own temp folder, never the repo, `X:\code` or a folder of their own, and are deleted once the PR merges. Shots the owner should see are sent to them; nothing is archived (the owner, 2026-10-31). At the end of a phase, follow `docs/end-of-phase-checklist.md`.
- **Installers:** made with `build/pack.ps1` (`build/README.md`) in a worktree. Every file is hashed against `phase-1-release-artifacts.csv`. Refresh them when the owner is about to install or at the end of a phase, not after every merge. During the owner's active test-and-fix loop, deliver refreshed installers with the completed fixes so he can test them (the owner, 2026-11-04). Before removing the pack worktree, copy its set over `X:\code\chippi\build\artifacts\releases\<version>\` (Git ignores it) and check each file against `artifacts.csv`: only the newest set is kept.
- **Live checks for the owner:** each step says how to make every test file, what to type and where to click.
- **Copy is terse, like a professional app (the owner, 2026-11-17, after repeating it many times):** labels, values and verbs only. No explanations, reassurance, consequences or "why" lines ("Deleted, not recycled. This can't be undone.", "ends the whole app", "verified to be Firefox's own", "Named like the app"), no "for good", no counts with prose ("3 items · matched by name only" is "3"). A confirm is the verb and its object ("Clean 3.9 GB?", "End node.exe?") with Cancel and the verb; a status is one or two words ("Kept", "In use", "Failed"). Errors read "… failed". Buttons are bare verbs. Controls stay compact: filters are a small dropdown, never a row of big buttons, and the UAC shield sits in its own narrow column, not inside a button or pill. Check every mockup and screen against this before showing it.
